# 画面ロック中・サインアウト中の無人実行（設計メモ・案）

状態：**案**（2026-11-07）。競合より劣る点 G18（[competitive-gaps.md](competitive-gaps.md)）の方式を決めるためのメモ。段階 1 から作り、段階 2 はコード署名のあとに決める。

## 1. いま困ること

- マウス・キーボードを使うノード（`desktop.mouseClick`・`desktop.type`・`desktop.press`・`desktop.drag` など、`desktop.input` を取るもの）は、画面がロックされている・サインイン画面・UAC の確認・リモートデスクトップの切断中だと `DESKTOP_UNAVAILABLE` ですぐ止まる（`crates/shikigami-desktop/src/session.rs`）。
- 夜のスケジュールでデスクトップのフローを動かすには、「PC をサインインしたまま、ロックしないで置いておく」しかない（[schedules.md](../schedules.md)）。会社の PC はたいてい数分でロックされる決まりがあるので、実際には使えない。
- サインアウトしている PC・再起動したあとの PC では、エージェント自体が動いていない（エージェントはユーザーのプロセス）。
- 仮想マシンのロボットをリモートデスクトップで見に行き、窓を閉じる（切断する）と、そのセッションはロックされたのと同じになる。窓を最小化しても描画が止まる。

すでに大丈夫なこと：

- UI オートメーションの操作（`desktop.click`・`desktop.setValue`・`desktop.getValue`・`desktop.select`・`desktop.check`・`desktop.selectMenu`・`desktop.getTable` など）は `desktop.input` を取らないので、ロック中でも止めていない。アプリの窓はロック中もユーザーのデスクトップにあり、UI オートメーションはマウスを使わないため。ただし実機では試していない（P0：実機検証）。
- ブラウザ・ファイル・Excel・メールなど、画面を使わないノードはロック中も動く。

## 2. 他の製品のやり方（調べた範囲）

| 製品 | やり方 | 前提 |
|---|---|---|
| UiPath（無人ロボット） | Windows のサービスとして常駐するロボットが、Orchestrator に預けた Windows の資格情報で **自分でセッションを作って** サインインし、終わったらサインアウトする。サーバー OS ではリモートデスクトップの仕組み、クライアント OS ではコンソールへのサインイン | 管理者によるインストール、ロボット用の Windows アカウント、Orchestrator |
| Power Automate Desktop（無人） | クラウドに預けた資格情報で、PC が **新しいセッションを作って** 実行する | Windows 10/11 では、その PC に誰もサインインしていないこと（ロック中のセッションがあっても失敗する）。有償の無人ライセンス |
| WinActor など | ロックしない設定・リモートデスクトップの切り方の工夫（`tscon` で切断してもロックしない）などで運用することが多い | 運用での工夫 |

どの製品も「ロックされた画面の上で操作する」のではなく、**操作できるセッションを用意する** ことで解いている。Windows はロック中の画面へのマウス・キーボードの入力を、ユーザーのプロセスに許さない（安全のための仕組み）ので、ここを回り道する方法はない。

## 3. 方式の比較

| 方式 | 何をするか | 資格情報 | クライアント OS（Windows 10/11） | 管理者 | 危うさ |
|---|---|---|---|---|---|
| (a) リモートデスクトップのループバック | 自分の PC に RDP でつなぎ、そのセッションで動かす | Windows のパスワードを PC に保存 | **使えない**（クライアント OS は同時に 1 セッションだけで、自分自身への接続は断られる） | 要（RDP の有効化） | 小さい。サーバー OS の VM なら一番素直 |
| (b) 自動サインイン | 起動時に決まったアカウントで自動でサインインする（Windows の自動ログオン） | パスワードを Windows の LSA に保存 | 使える | 要 | ロックされたら同じ問題に戻る。サインインしたまま放置になる |
| (c) ロックを解いて、終わったらロックし直す | 資格情報プロバイダー（Windows のサインイン画面の部品）を入れ、実行の間だけロックを解く | Windows のパスワードを PC に保存 | 使える | 要（DLL の登録） | **大きい**：解いている間、PC の前の人に画面が見え、触れる。サインイン画面に入る部品なので署名が無いと会社の PC では入れられない |
| (d) サービスがセッションを作る（UiPath・PAD と同じ形） | Windows サービスが、誰もサインインしていない PC にロボット用アカウントでサインインし、終わったらサインアウトする。クライアント OS は (c) と同じ資格情報プロバイダー、サーバー OS は (a) | ロボット用アカウントのパスワードを、サービスだけが読める所に保存 | 使える（誰もサインインしていないとき） | 要 | 中くらい：ロボット用 PC・VM で使う前提。サービスは SYSTEM 権限 |
| (e) 運用の手当て | ロックさせない・RDP を切ってもロックさせない・最小化しても描画を止めない | 不要 | 使える | `tscon` だけ要 | 小さい。ただし PC の前に人がいれば画面が見える（今と同じ） |

## 4. 決めたいこと（推奨）

**段階 1（資格情報を持たない手当て）を先に作り、段階 2（サービスがサインインする）はコード署名のあとに決める。**

理由：

- 段階 2 は Windows のサインインの仕組みに入る部品（資格情報プロバイダー・SYSTEM のサービス）で、署名の無い DLL は会社の PC ではまず入れられず、ウイルス対策ソフトにも止められやすい。署名（SignPath Foundation を予定）の前に作っても、使ってもらえる所がない。
- 段階 1 だけでも、「ロボット用の VM に RDP で入って様子を見て、切断して帰る」「事務所の PC で昼休みにロックされて止まる」という、今いちばん多い困りごとが解ける。資格情報を預からないので、危うさが増えない。
- 段階 2 の形（サービス＋ロボット用アカウント＋サインアウトまで）は、段階 1 と食い違わない。エージェントのジョブの受け付け（[remote-runs.md](remote-runs.md)）はそのまま使える。

### 段階 1：資格情報を持たない手当て

1. **実行中は画面オフ・スリープさせない。**（済み） `desktop.input` を取るノードがあるフローの実行中は、Windows に「表示と PC が使われている」と伝える（電源要求 `PowerSetRequest` の表示と PC）。画面が消える・スリープして、復帰にサインインが要る、で止まるのを防ぐ。実行が終われば元に戻る。
   - **ロックそのものは止めない。** パスワード付きのスクリーンセーバー（電源要求でも止まらないと Microsoft の文書にある）と、グループポリシーの「コンピューターの非アクティブ状態の制限」は会社が決めた安全の設定なので、Shikigami が無効にしたり、入力を偽って時間を延ばしたりはしない。これらがある PC では、5 で前もって知らせ、2・4 や段階 2 で手当てする。

5. **前もって知らせる。**（済み：パスワード付きスクリーンセーバーと非アクティブ状態の制限。スケジュールの一覧の画面ロック中の表示はまだ） Studio の「自動実行」で、デスクトップの操作を含むフローに予定を入れるとき、この PC のパスワード付きスクリーンセーバー・非アクティブ状態の制限のロックまでの時間を読んで、「このままだと○分でロックされて止まります」と出す。スケジュールの一覧の状態にも「画面ロック中：デスクトップのフローは止まります」を出す（エージェントはすでに `desktop_available` を持っている）。

### 段階 2：サービスがロボット用アカウントでサインインする（署名のあと）

- `shikigami agent --service` を Windows サービスとして入れられるようにする（管理者がインストーラーの選択肢で選ぶ）。サービスは SYSTEM で、フローは動かさない。セッションを用意して、そのセッションの中で今のエージェントを動かすだけ。
- ロボット用アカウントのパスワードは、サービスだけが読める所（LSA の秘密、または DPAPI のマシン鍵）に保存する。Shikigami のシークレット（[secrets.md](../secrets.md)）とは混ぜない。管理サーバーにも出さない。
- デスクトップのジョブが来て、誰もサインインしていなければサインインし、終わったらサインアウトする。誰かがサインインしているときは、そのセッションを横取りしない（PAD と同じく、デスクトップのジョブは受けない＝ほかの PC に回る）。
- クライアント OS では資格情報プロバイダー、サーバー OS ではループバックの RDP。どちらも署名した DLL・実行ファイルだけで配る。
- `policy.json` で、この PC がサインインまでしてよいか（既定はしない）を決める。監査（[audit.md](../audit.md)）に、いつ誰のアカウントでサインインしたかを残す。

## 5. 決めないこと・やらないこと

- ロックされた画面の上で、ドライバーなどを使って入力を送り込むことはしない（Windows の安全の仕組みを壊すことになり、会社では使えない）。
- 段階 1 の 2（`tscon`）を、実行のたびに自動で行うことはしない。人がリモートデスクトップを閉じるときの操作として出す。

## 6. 進め方

1. 段階 1 の 1（実行中は画面オフ・スリープさせない）と 5（前もって知らせる）：小さく、資格情報も管理者も要らない。最初の PR。
2. 段階 1 の 2・3（リモートデスクトップ）：`shikigami session` と Studio のボタン。
3. 段階 1 の 4（ロック解除を待つ）：`policy.json` の項目なので、スキーマと CHANGELOG に書く。
4. 段階 2：コード署名が済んでから、Daiki と範囲を決める。
