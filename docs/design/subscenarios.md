# サブシナリオ（処理をまとめて呼び出す）（設計メモ）

方針：長いフローの一部を **別のシナリオ** に切り出し、呼び出し側では 1 つのノードに畳む。部品は入力と出力をはっきり持ち、何度でも使い回せる。新しい「部品」の種類は作らず、呼び出される側も普通のシナリオにする（版・書き出し・レビュー・単体実行がそのまま使える）。

## 1. 書き方（1 通りだけ）

```json
{
  "type": "scenario.call",
  "name": "請求書を 1 件登録する",
  "params": {
    "scenario": "scn_01a1…",
    "inputs":  { "invoice": "{{ invoice }}", "dryRun": false },
    "outputs": { "registeredNo": "invoiceNo" }
  }
}
```

| param | 意味 |
|---|---|
| `scenario`（必須） | 呼び出すシナリオの ID（`list_scenarios` の `id`）。名前では指さない |
| `inputs` | **キー＝呼ばれる側の入力変数**、値＝渡す値。値はほかの param と同じくテンプレート（`"{{ invoice }}"` のように全体が 1 つの `{{ }}` なら型を保つ）。リテラルも可 |
| `outputs` | **キー＝呼ばれる側の出力変数**、値＝受け取る呼び出し側の変数名 |

- どちらの対応表も「キーは呼ばれる側の変数」。向きで迷わない。
- `saveAs` は使わない（受け取り方を `outputs` の 1 通りにする）。付けたら検証エラー。
- 呼ばれる側の変数は呼び出し側から見えない。受け渡しは `inputs` と `outputs` だけ。呼ばれる側の中で何を書いても、`outputs` に書いたもの以外は呼び出し側に残らない。
- 呼ぶたびに **その時点の最新内容** を使う。版番号での固定はしない（書き方を 2 通りにしないため）。実際に使ったリビジョンと一致する版番号は実行レポートに残す（§4）。

## 2. 検証

シナリオ単体で分かるもの（`Validator`）と、ワークスペースの他のシナリオを見ないと分からないもの（`ScenarioService::validate`）に分ける。Runtime も開始時に、渡された呼び出し先で同じ検査をする。

| コード | 重さ | 条件 | ヒントの例 |
|---|---|---|---|
| `INVALID_PARAMS` | error | `scenario` がない、`outputs` の値が変数名でない | スキーマと記述例 |
| `CALL_SAVE_AS` | error | `saveAs` が付いている | `outputs: { "<出力>": "<変数>" }` で受け取る |
| `CALL_RETRY` | error | `retry` が付いている | 再試行は呼ばれる側のステップに付けるか `control.try` で包む |
| `CALL_TARGET_NOT_FOUND` | error | ID のシナリオがない（削除済みを含む） | `list_scenarios` で ID を確かめる。ゴミ箱から戻せる |
| `CALL_CYCLE` | error | 呼び出しが自分に戻ってくる（A→B→A、自分自身） | 共通部分をさらに別のシナリオに切り出す |
| `CALL_TOO_DEEP` | error | 呼び出しの深さが 16 を超える | |
| `CALL_TARGET_INVALID` | error | 呼ばれる側に検証エラーがある | `validate_scenario` で呼ばれる側を直す |
| `CALL_UNKNOWN_INPUT` | error | `inputs` のキーが呼ばれる側の入力でない | 呼ばれる側の入力の一覧（近い名前があれば「もしかして」） |
| `CALL_MISSING_INPUT` | error | 既定値のない入力を渡していない | 同上 |
| `CALL_INPUT_TYPE` | error | リテラルの値が入力の型に合わない | |
| `CALL_SECRET_LITERAL` | error | `secret: true` の入力に文字列をそのまま書いた | 呼び出し側の secret 変数から `{{ }}` で渡す |
| `CALL_UNKNOWN_OUTPUT` | error | `outputs` のキーが呼ばれる側の出力でない | 呼ばれる側の出力の一覧 |

- `outputs` の値は、`saveAs` や `variable.set` と同じく「その変数への書き込み」として扱う。`control.parallel` のブランチ間の競合（`PARALLEL_VARIABLE_CONFLICT`）や、並列 forEach の共有書き込み（`FOREACH_SHARED_WRITE`）もこれで検出される。
- 呼び出されているシナリオは削除できない（`SCENARIO_IN_USE`、呼び出し元の一覧付き）。先に呼び出しを外す。

## 3. 実行

- Runtime はワークスペースを読まない。実行する側（Studio・MCP・CLI）が開始時に呼び出し先をたどって集め（`ScenarioService::subscenarios`）、`RunOptions.subscenarios` で渡す。**実行中に呼ばれる側が編集されても、その実行には影響しない。**
- 呼び出しのたびに、呼ばれる側の変数を新しく作る（入力 → 既定値 → なしは null。`MISSING_INPUT` などは単独実行と同じ）。設定（既定のタイムアウト・再試行・onError）も呼ばれる側のものを使う。
- 終わったら呼ばれる側の出力変数を `outputs` の対応で呼び出し側に書き込む。失敗したときも、呼ばれる側がそれまでに代入した出力だけは書き込む（その場で実行したときと同じく、catch や `onError: continue` の後から見える）。
- 中止：呼び出し側の中止はそのまま呼ばれる側に伝わる。
- タイムアウト：`timeoutMs` を付けたときだけ、呼び出し全体の上限になる（既定の 30 秒は掛けない。中のステップにはそれぞれのタイムアウトが効く）。超えたら `STEP_TIMEOUT`。
- 失敗：呼ばれる側で失敗すると、呼び出しステップの失敗になる（コードとメッセージはそのまま。`details.subScenario` に失敗した場所 `{ scenarioId, scenarioName, stepId, stepType }`）。呼び出し側の `onError: continue` と `control.try` が効く。
- 排他ロック：ロックはステップ単位で、同じ Runtime の全実行で共有。呼び出しステップ自体はロックを持たないので、呼ぶ側と呼ばれる側でデッドロックしない。
- `break` / `continue` は呼び出しの境界を越えない（呼ばれる側の最上位にあれば、その側の `NOT_IN_LOOP`）。
- 秘密の値：同じ実行の中で共有されるので、呼ばれる側で分かった秘密は呼び出し側のログでも伏せ字になる。
- イベント：呼ばれる側のステップのイベントは、エンベロープの `callPath`（呼び出しステップ ID の列、外側から）が付く。最上位のイベントは `callPath` なし。Studio はこれで呼び出し側の図とたたんだ中身を描き分ける。
- 実行レポートの `subscenarios` に、使ったシナリオの ID・名前・リビジョン・一致する版番号を残す。

## 4. 版・共有・レビュー

- 版：呼び出し側の版は呼ばれる側を含まない（ID で指すだけ）。呼ばれる側の版は呼ばれる側で管理する。復元しても他方は変わらない。
- 書き出し：バンドルに `subscenarios`（呼び出し先をたどったすべて。版なし、secret の既定値は消す）を入れる。`shikigami run <bundle>` はそのまま動く（バンドルの中のものを優先し、それらが呼ぶものはワークスペースからたどる）。
- 取り込み：`subscenarios` はそれぞれ、ID がなければ同じ ID で作成、あれば `onConflict: "update"` のときだけ更新し、それ以外は既存のものを使う。結果に一覧（`created` / `updated` / `kept`）を返す。
- レビュー：呼び出しも普通のステップなので、AI の変更の「残す / 差し戻す」はそのまま使える。切り出し（§5）は「新しいシナリオの作成」と「呼び出し側の 1 回の編集」の 2 つの変更として記録に残る。
- プラグイン：`scenario` はプラグイン名に使えない（予約済み）。

## 5. 切り出し（`extract_subscenario`）

同じブロックに並んだステップをまとめて新しいシナリオにし、元の場所を `scenario.call` に置き換える。Studio の「サブシナリオにまとめる」と MCP の `extract_subscenario` が同じ Core の処理を使う。

- 入力：切り出す部分が読む変数のうち、呼び出し側で宣言されているか、切り出す部分の外で書き込まれるもの（中の loop 変数・`errorVar` を除く）。
- 出力：切り出す部分が書き込む変数のうち、外で読まれるか、呼び出し側の出力変数であるもの。loop 変数・`errorVar` も外から見えるなら出力にする（変数のスコープは平らなので、ループの後には最後の要素が残る）。
- 型と `secret` は呼び出し側の宣言を引き継ぐ。宣言がなければ `any`。
- 呼び出しステップは `inputs: { x: "{{ x }}" }` と `outputs: { y: "y" }` で、元と同じ変数を読み書きする。動きは変わらない。
- 呼び出し側の編集は 1 回なので、Undo で元に戻る（作った新しいシナリオは残る）。

## 6. Studio

- 呼び出しノード：見出しに呼ぶシナリオの名前。行は入力（呼ばれる側の入力名 : 値、入力ソケット付き）と出力（変数ソケット付き）。
- 「中を見る」でノードの下に呼ばれる側のステップを読み取り専用で描く（もう一度押すと畳む）。「開く」で呼ばれる側に移る。
- 呼び出しノードをダブルクリックすると、その場で図が呼ばれる側のフローに入る（読み取り専用）。中の呼び出しにもさらに入れる。上のパンくず（親 › 子 › 孫）か ↑・Esc・Backspace で戻る。編集はパンくずの「開く」から。編集用のツール（ステップ追加など）は入っている間は出さず、目次やパレットから開いているシナリオのステップを選ぶと最上位に戻る。
- 実行中は、`callPath` のないイベントで呼び出し側の図を、`callPath` のあるイベントで呼び出しの中（畳んだ中身・入った図）の進み具合を出す。中の状態は `callPath` 全体ごとに持つので、入れ子の呼び出しに入っても進み具合が見える。入った図でも実行中のステップを追う。「追う」がオンなら、実行が呼び出しの中に入ると図も自動でその中へ入り、呼び出し側に戻ると図も戻る（入れ子も同じ）。図を手で動かすと「追う」が切れ、図は人が置いた所にとどまる。
- 呼ばれる側は Runtime がデバッガなしで動かすため、入った図の中ではブレークポイント・一時停止はできない（呼び出しステップ単位で止まる）。
- プロパティ：呼ぶシナリオを一覧から選ぶ。選ぶと、呼ばれる側の入力・出力の行を出し、それぞれに値と受け取る変数を書く。
- 複数のステップを選んで「サブシナリオにまとめる」。
