# エラーで止まる実行とステップ実行

Studio から実行したフローは「対話的な実行」になる。失敗しても黙って終わらず、その場で一時停止して、人が見て、AI に直してもらい、止まったところから続けられる。ブレークポイントとステップ実行も同じ仕組みで動く。CLI・MCP・将来のスケジューラーからの無人実行はこれまでどおり失敗で終わる（`RunOptions.debug` を渡さない）。

## どこで止まるか

- **処理されないエラー**：手順が（リトライも使い切って）失敗し、その失敗を受け止めるものがないとき。`control.try` の `catch` の中、`onError: continue` の手順、`onError: continue` の `wait.until` の `check` の中のエラーでは止まらない。
- **ブレークポイント**：その手順を実行する直前。Studio のノード左上の赤い点（F9）で付け外しし、実行中でもすぐ効く。PC ごとに保存。点にマウスを置くと意味が出る。まとめて外すのは実行ログの上かフロー図の地の右クリック「ブレークポイントをすべて外す」。
- **ステップ実行**：「ステップ実行」（F10/F11）で最初の手順の前から始める。次へ（F10, ブロックの中も含めて実行して同じ深さ以上の次の手順で止まる）、中へ（F11, 次に実行する手順で止まる）、外へ（Shift+F11, 今のブロックを最後まで）、続行（F5）、飛ばす。
- **一時停止ボタン**：実行中に押すと次の手順の前で止まる。

止まっている間は何も動かず、タイムアウトも数えない。ブラウザなどアダプターの状態はそのまま残る。

## 止まったときに見えるもの

Runtime は `paused` イベント（`stepId`、理由、エラー、その時点の全変数（秘密は `***`）、実行中のリビジョン）を出す。Studio は失敗したノードを赤く囲んで画面に寄せ、下にパネルを出す。エラーで止まったときは、Studio がアダプターの `inspect` でその実行のブラウザ／ウィンドウを見て、スクリーンショットと画面ツリーを観察（`source: runPause`）として記録する。

止まっているあいだは、パネルの変数をクリックして値を変えられる（UiPath の Locals パネルの値の変更にあたる）。Studio は `setVariable` コマンド（`name`・`value`）を送り、Runtime は再開する前にその値を入れて、ノードなしの `variableChanged` として記録する。文字列の変数は打った文字のまま、それ以外は JSON（`123`・`true`・`[1, 2]`）として読む。シークレットの変数と、`paused` で一部だけ届いた長い値（1000 文字超）は変えられない（`VARIABLE_NOT_EDITABLE`）。呼び出したフローの中で止まったときは、そのフローの変数が対象になる。

## AI に直してもらう

「AIに直してもらう」は、エラー・失敗した手順の params・変数・止まった画面のツリー・観察 ID・runId をまとめた依頼文を作る（`lib/fixRequest.ts`）。Studio の AI ペイン（`agent.ts`）が使えるときはそのまま AI に送り（失敗した手順を `stepId` として添える）、使えないとき（エージェントが見つからないなど）はクリップボードにコピーする。AI がほかの依頼に取り組んでいるあいだはボタンを押せない。AI の MCP サーバーは別プロセスで、止まっているブラウザは見えないので、画面ツリーを文面に入れる。AI が観察 ID を編集の `observations` に付けると、確認待ちで根拠の画面として見える。AI は `get_run_logs` でこの実行の記録も読める。

AI の修正は通常どおり確認待ちに入る。未確認の AI の変更があるあいだは再開ボタンを押せない（未確認のものを実行しないため）。承認すると「直した内容で再開」になる。

## 途中でのフロー変更と再開の安全性

再開（もう一度／続行／ノード／飛ばす）のたびに、Studio は保存されている最新リビジョンを実行に渡す（`DebugControl::update_flow`）。受け入れる条件：

1. 検証エラーがない。
2. 実行が今いる位置が新しいリビジョンにもある。今いる各ブロックが同じ ID・同じ種類の手順にぶら下がり、その手順が外側のブロックの中に残っていて、各ブロックで最後に終わった手順も同じブロックに残っていること。

満たさないときは `RESUME_INCOMPATIBLE` で断り、実行は元のリビジョンのまま止まり続ける（止めて最初から実行し直す）。

受け入れたあとは、各ブロックの「次の手順」を毎回新しいリビジョンから読む（`Executor::live_block`）。だから

- 失敗した手順をもう一度実行すると、直した定義で動く。
- 失敗した手順の前（同じブロックの、最後に終わった手順のあと）に足された手順から先に動く。
- これから実行する手順の変更はそのまま効く。
- 変数の値はそのまま。新しく宣言された変数は既定値で入る。フロー設定（既定のタイムアウトなど）も新しいものになる。
- すでに始まっている制御ノードが読んだもの（ループの条件・`forEach` の items・`if` の分岐）は変わらない。

## 並列

止まるのは実行の本線だけ。`control.parallel` の枝や `concurrency` 付き `forEach` の各回は止まらずに走りきり、その中のエラーは `control.parallel` / `control.forEach` の手順で止まる。「もう一度」はその手順を丸ごともう一度実行する。

## ログからノードへ

ノードには新しい番号を付けない。ID はすでに `stepId`（保存したフローの中で変わらない）があり、ログ・イベント・エラーはどれもそれを持っている。足りなかったのは、人が読む側の名前と、押して飛ぶ仕組みのほう。

- 連番（Power Automate for desktop の行番号のようなもの）は、ノードを足すたびにずれ、前の通知やログが別のノードを指すようになる。フロー図にも番号を並べることになり、見た目が重くなる。
- 人が読む名前は、フロー図に出ている名前（表示名、なければ一文）。n8n がノード名でログを示すのと同じ。同じ名前があっても Studio では押せば分かる。
- 画面に `stp_…` や英語のエラーコードは出さない（wording.md）。ID は押したときの行き先として裏に持つ。

| 出る場所 | ノードの示し方 |
| --- | --- |
| Studio の実行ログ | ノード名（サブフローの中は「サブフロー名 › ノード名」）。押すとそのノードへ（`goToPlace`、サブフローには入って見せる） |
| 失敗・一時停止のパネル | 同じ。サブフローの中で失敗して終わったときは `details.subFlow` から中のノードを探す（`errorPlace`） |
| 通知（Teams・Slack） | 「ノード: 「出荷」→ サブフロー「出荷の入力」の「送信ボタン」」。JSON 形式は `stepId` と `stepLabel` の両方 |
| `shikigami run`・`shikigami test` | `請求書の保存 [stp_013_save]`。人は名前で、AI と開発者は ID で探す |
| `logs/` の読むためのログ | 以前から `名前 [種類 ID]` |
| 実行の記録（`runs/`）・MCP | `stepId`。終わりのエラーには `stepLabel` も入る。AI は ID でノードを特定する（ai-authoring.md） |
